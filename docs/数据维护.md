# 数据维护

适用于 v1.2。所有命令由 `go-monitor.exe` 独立执行，无需 Go、Node 或外置 SQLite 工具。正式制品来源、hash及复验按对应Release记录核对。

## 操作前

在程序目录打开 PowerShell 7。需要导出历史时，先按[历史导出](#历史导出)一节查询并记录目标ID。之后在监测窗口按 Ctrl+C，等待服务正常退出，再执行维护命令。工具不强制结束进程，也不能仅凭进程编号证明旧程序已经停止。

输入文件与输出目录必须存在。输出文件必须是新文件；恢复及配置导入的数据库路径和对应 `-wal`、`-shm`、`-journal` 文件均不能已经存在。遇到拒绝覆盖时选择新路径，不要删除不明来源的侧车文件。

```powershell
.\go-monitor.exe maintain help
```

每条维护命令最多运行2分钟，可按 Ctrl+C 取消。备份压缩、解压总量各最多256MiB，清单最多64KiB；只接受工具的两条目 ZIP 格式，不接受 ZIP64 或多磁盘 ZIP。配置输入最多4MiB、100个目标。目标文件通过同目录临时文件与原子硬链接发布；不支持硬链接的文件系统会明确失败，不降级为覆盖写入。

## 完整备份、验证和恢复

```powershell
.\go-monitor.exe maintain backup -db data/monitor.db -out backup.zip
.\go-monitor.exe maintain verify -in backup.zip
.\go-monitor.exe maintain restore -in backup.zip -db data/restored.db
```

备份包含目标、规则、历史、日汇总和元数据，并覆盖尚在 WAL 中的已提交记录。它含原始网址和其他原始数据；SHA-256用于完整性校验，不是加密。不要将真实备份提交或公开上传。

验证包括归档结构、大小、校验和、SQLite完整性、外键和计数。恢复保留备份的schema版本、ID和逻辑数据，不覆盖当前数据库。成功后选择相应程序打开新路径：

```powershell
.\go-monitor.exe serve -db data/restored.db
```

真正启动时才进行程序支持的迁移及明细保留清理，恢复本身不迁移、不淘汰过期记录。备份已不包含的历史无法恢复。

从 v1.1 升级：停止 v1.1，用新维护命令备份并验证schema3库，再用新程序启动原库升级到schema4。回退：停止新程序，将升级前schema3备份恢复到新路径，再用 v1.1 打开恢复路径。v1.1不能直接打开schema4。

## 配置迁移

默认导出脱敏文件，供查看或分享；它不能直接导入。

```powershell
.\go-monitor.exe maintain export-config -db data/monitor.db -out config-redacted.json
```

需要真实迁移时显式导出完整配置，并妥善保管：

```powershell
.\go-monitor.exe maintain export-config -db data/monitor.db -out config-full.json -full
.\go-monitor.exe maintain import-config -in config-full.json -db data/imported.db -dry-run
.\go-monitor.exe maintain import-config -in config-full.json -db data/imported.db
```

预检会报告目标数量、来源启用数、导入后启用数及策略，不创建数据库。正式导入也先预检，再将全部目标一次性写入全新数据库。任一目标失败，整个导入失败，不留下部分目标。

导入默认暂停全部目标。确需保留来源启用状态时，在预检和导入命令中都加 `-keep-enabled`。之后用 `serve -db data/imported.db` 打开，再按需启用目标。

配置文件版本为1，包含生成时间和敏感信息标记。未知字段、未知版本、缺失配置、非法规则、脱敏标记或占位内容都会被拒绝。完全相同的规范化配置不能重复；同网址不同规则或间隔可以并存。导入重新分配ID，不导入历史或汇总；需要保留它们时使用完整数据库备份。

## 历史导出

目标ID不是列表中的序号，删除后也可能不连续。在监测服务仍运行时，通过只读目标列表查询ID；自定义端口时替换下面的8080。先将返回数组赋给变量，再选择ID、名称和展示地址，不直接打印完整原始配置：

```powershell
$targets = Invoke-RestMethod 'http://127.0.0.1:8080/api/targets'
$targets | Select-Object id, name, display_url
```

记录需要的ID后，在监测窗口按 Ctrl+C，等待服务正常退出，再运行维护导出。将示例中的 `-target 1` 替换为实际ID，`-db` 指向刚才查询的同一监测数据库。明确指定UTC开始和结束时间；开始包含、结束不包含，开始必须早于结束。

```powershell
.\go-monitor.exe maintain export-history -db data/monitor.db -out history.json -target 1 -from 2026-11-01T00:00:00Z -to 2026-11-02T00:00:00Z
.\go-monitor.exe maintain export-history -db data/monitor.db -out history.csv -target 1 -from 2026-11-01T00:00:00Z -to 2026-11-02T00:00:00Z -format csv
```

仅导出仍保留且未过期的明细，以检查开始时间 `checked_at` 为口径。读取来自一致快照，跨分页不会漏项或重复；不会补造已淘汰或未采样数据，也不提供历史导回功能。

JSON带范围元数据和 `checks`。CSV固定表头，第一条数据行为 `record_type=metadata`，其余样本行为 `record_type=check`；在表格软件中筛选后者分析样本。每行包含目标ID、UTC范围与保留口径，空导出仍保留metadata行，不把它算作检查样本。耗时单位为毫秒，空值保留未知含义；规则快照保留精确数字。文本字段有公式注入防护，可能以单引号开头。

默认导出使用与页面一致的URL及错误说明脱敏。其范围不包括自动识别任意目标名、URL路径或规则值中的秘密；导出前仍应检查这些内容。

## 保留范围与失败处理

每目标明细受1000条和30天共同限制，先达到哪个限制就受哪个约束。理论覆盖时长按间隔估算并以30天封顶，不含请求耗时、停机或排队：60秒间隔约16.7小时，5秒间隔约83分钟。页面历史同时显示实际最早/最新明细与当前条数；UTC日汇总无法还原被淘汰的逐条明细。

维护退出码：0成功，1操作失败，2参数错误。错误会说明不存在、权限、取消、超时、数据库锁或校验/格式问题。修正原因后使用新的输出路径重试；失败目标不会被当作成功文件发布。不要把保存失败的临时文件当成备份。正常完成后工具会清理自身临时文件；操作系统或进程异常终止可能留下私有临时文件，不代表操作完成。
